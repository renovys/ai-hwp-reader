# HWP 파싱 노트 — 그럴듯하게 틀리는 자리들

한글 문서를 직접 파싱할 때 가장 위험한 실패는 예외가 아니라 **결과가 멀쩡해 보이는데 틀리는 것**입니다. hwp-reader에서 실제로 회귀 시험으로 고정한 주요 함정을 정리합니다.

## HWP 5.0 파일 구조

HWP 5.0은 OLE Compound File Binary 안에 레코드 스트림을 담습니다. 일반 문서는 `BodyText/SectionN`에 본문이 있고 `FileHeader`의 속성에 따라 raw DEFLATE로 압축됩니다.

주요 태그:

| 값 | 이름 | 내용 |
|---|---|---|
| 66 | `PARA_HEADER` | 문단 시작 |
| 67 | `PARA_TEXT` | UTF-16LE 문단 글자 |
| 71 | `CTRL_HEADER` | 표·메모 등 개체 제어 |
| 72 | `LIST_HEADER` | 표 셀 정보 |
| 77 | `TABLE` | 표 크기 정보 |
| 93 | `MEMO_LIST` | 메모 본문 |

레코드 헤더는 4바이트이며 태그 10bit, 레벨 10bit, 크기 12bit입니다. 크기가 `0xFFF`면 다음 4바이트가 실제 payload 크기입니다. payload가 섹션 끝을 넘어가면 손상된 문서로 처리해야 합니다. 일부만 읽고 성공으로 끝내면 누락을 알아채기 어렵습니다.

## 함정 1 — 셀 좌표는 LIST_HEADER 오프셋 8부터

셀 속성은 다음 위치에서 시작합니다.

```text
offset  8 : col
offset 10 : row
offset 12 : colspan
offset 14 : rowspan
```

오프셋 0부터 읽으면 단순 표는 얼핏 정상처럼 보여도 2단 헤더에서 열이 밀립니다. 금액표처럼 병합이 많은 문서에서는 치명적입니다.

자가 진단: 모든 셀의 `row`가 0이거나 병합 값이 비정상적으로 크면 오프셋을 먼저 확인합니다.

## 함정 2 — PARA_TEXT 제어문자의 폭이 다르다

`PARA_TEXT`에는 글자와 개체 제어가 섞여 있습니다.

- `0`, `10`, `13` → 1워드
- `1~23` 중 위 세 값을 제외한 제어 → 8워드

8워드 제어를 1워드로 건너뛰면 뒤의 이진 데이터가 한자나 옛한글 같은 글자로 새어 나옵니다.

제어 시퀀스를 건너뛴 뒤에도 실제 문서의 글자 스트림에 `U+001F` 같은 C0 문자가 남을 수 있습니다. 이것은 이미 UTF-16 문자로 읽힌 뒤의 잔여 제어이므로 출력 단계에서 공백으로 정리합니다.

## 함정 3 — UTF-16 서로게이트 쌍

코드 유닛을 하나씩 `chr()`로 바꾸면 BMP 밖 문자가 깨질 수 있습니다. 일반 글자 구간을 바이트로 모은 뒤 `utf-16-le`로 한 번에 디코딩합니다.

```python
run += payload[i * 2:i * 2 + 2]
text = run.decode("utf-16-le", "replace")
```

## 함정 4 — 섹션 이름을 문자열로 정렬하면 문서 순서가 틀어진다

`Section0`, `Section1`, `Section2`, … `Section10`을 단순 `sorted()` 하면 `Section10`이 `Section2`보다 앞에 옵니다. HWP와 HWPX 모두 끝의 숫자를 정수로 읽어 정렬해야 합니다.

```text
잘못: Section0, Section1, Section10, Section2
정상: Section0, Section1, Section2, Section10
```

## HWP 메모(주석)

HWP 메모는 자리 표시와 본문이 나뉩니다. 본문의 `%unk` 제어가 메모 위치를 가리키고, 실제 메모 글자는 섹션 뒤쪽의 `MEMO_LIST` 이후 문단에 들어갑니다. 하나만 읽으면 위치나 내용 중 하나를 잃습니다.

hwp-reader는 메모가 달린 셀에 `⟨메모⟩`를 남기고, 실제 본문은 `[메모]` 블록으로 출력합니다.

## HWPX는 XML이지만 셀 주소를 봐야 한다

HWPX는 ZIP 안의 OWPML XML입니다.

- 본문: `Contents/sectionN.xml`
- 문단: `<hp:p>`
- 글자: `<hp:t>`
- 표: `<hp:tbl>` → `<hp:tr>` → `<hp:tc>`

### 함정 5 — `<hp:tc>`가 나온 순서가 열 위치가 아니다

병합 표에서는 위 행의 `rowSpan`이 아래 행의 칸을 이미 차지합니다. `<hp:tc>`를 보이는 순서대로 0번 열부터 채우면 열이 왼쪽으로 밀립니다.

가능하면 `cellAddr`의 `rowAddr`·`colAddr`을 사용하고, 주소가 생략된 문서에서는 이미 놓인 셀의 병합 범위를 피해 커서를 이동합니다.

### 함정 6 — 표 안 문단을 본문으로 다시 읽기 쉽다

셀 안의 텍스트도 `<hp:p>`로 표현됩니다. XML 전체의 `<hp:p>`를 평평하게 순회하면 표가 표 블록으로 한 번, 일반 본문으로 한 번 더 나옵니다. 표를 만나면 그 자식 문단을 일반 본문 순회에서 제외해야 합니다.

자가 진단: 표 셀 값이 표 바로 뒤에 같은 순서로 다시 나타나면 이 문제입니다.

### 함정 7 — 문단 내부 메모 처리에서 부모를 다시 순회하면 중복된다

메모가 문단 중간에 들어간 경우 메모를 처리하기 위해 부모 노드를 다시 순회하면 메모 앞뒤 텍스트나 형제 노드를 두 번 읽을 수 있습니다. 메모 노드 자체만 별도 처리하고, 메모 전후의 텍스트 버퍼를 끊어 문서 순서를 보존해야 합니다.

예상 블록 순서:

```text
본문 앞
[메모] 검토 내용
본문 뒤
```

## Markdown 출력도 구조의 일부다

셀 안에 실제 `|` 문자가 있으면 그대로 이어 붙인 Markdown은 열 하나를 추가한 것으로 해석됩니다. 셀 값의 `|`와 백슬래시는 이스케이프해야 표의 열 수가 유지됩니다.

## 자가 검증 원칙

- 2단 이상 병합 헤더로 열 위치를 확인합니다.
- 본문과 표가 중복되지 않는지 확인합니다.
- 메모가 본문과 분리되고 위치 정보가 남는지 확인합니다.
- 다중 섹션을 숫자 순서대로 읽는지 확인합니다.
- 출력에 C0 제어문자나 `�`가 남는지 확인합니다.
- 손상된 레코드를 부분 성공으로 처리하지 않는지 확인합니다.
- `skill/hwp_reader_single.py`와 `SKILL.md` 코드블록은 직접 고치지 않고 `tools/build_single.py`로 생성합니다.
